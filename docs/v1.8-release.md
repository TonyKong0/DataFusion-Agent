## 一、范围

最后一轮不扩能力，只做三件能被证明的事：把两项 `unmeasured` 指标测出来、把「答案超出 SQL 证明范围」的已知缺陷关掉、把性能口径从冷启动污染中分离出来；与之并行完成技术报告。中期项（HAVING 级聚合比较、派生表与相关子查询、真实扫描件标注集、云端持续集成、视觉模型）全部推出本轮，理由写入报告第 5 章，不静默丢弃。

## 二、主线 A：30 题分层黄金集与两项指标补测

- 30 题按 S1 12 / S2-A 6 / S2-B 8 / S2-C 4 分层；候选判据由 MySQL 直查与材料原文预填，**用户 11-08 确认 30 行全 ✅、无逐行修改**后落成 `backend/tests/golden_answers_v1.8.json`（`status=human-confirmed`），`cases` 与 draft 逐字段一致，由 `test_golden_answers_v1_8_confirmed.py` 守门。draft 保留但恒为 `metrics_eligible=false`，机制上排除 AI 自标自测。
- 评测脚本新增分层取样、`judge_citation` 与 `judge_faithfulness` 逐题判分、澄清语义标记；固定三份文本型材料（`07_store_faq.txt`、`08_chinook_data_dictionary.md`、`04_invoice_review_example.docx`）并写入 `environment`。原 v1.7 固定取 `document_ids[0]`（仅一行 OCR 标记）导致引用判分无证据基础的问题已消除。
- 修正口径偏差：S2-C 4 题不再计入 `live_answer_accuracy`，答案准确率分母 26、澄清正确性分母 4 分别可回源。
- 真实 LLM 全量重跑：`docs/evaluation_agent_v1.8_live.json`，30 题、71 次 API 请求、未截断；逐题 verdict、引用/忠实度判定、all/cold/warm 延迟分组与 token 用量均可回查。

## 三、主线 B：答案生成的 SQL 语义约束

- 缺陷源头定位为三处 `chat(ANSWER_SYSTEM, …)`（`nl2sql_service.py` 两处、`multitable_service.py` 一处）把用户原问与 SQL 同时交给模型；跨源 `answer_composer` 为确定性模板，不产生该缺陷。
- 新增 `backend/app/services/answer_semantic_guard.py`：sqlglot 解析比较层级，按句剔除越界结论、保留可证明事实，带否定语境豁免与 fail-closed 解析失败处理；`ANSWER_SYSTEM` 增补约束条款，提示词载荷注入 `sql_semantics`，三处调用点接入 `answer_guard`。16 个正反例含 11-05 真实过度解读夹具。
- **未改动 `scalar_subquery.py`，未开放 HAVING / 派生表**；仅覆盖 SQL 语义越界，文档侧越界由主线 A 测量而非修复。
- 真实 LLM 端到端复跑：原始问法「查询消费总额高于全体客户平均消费额的客户姓名」的回答明确写出「并不能证明这些客户的消费总额高于全体客户的平均消费总额」；演示话术仍返回客户名单并附边界说明，未被误杀。本次由提示词层约束生效，fail-closed 守卫因答案含否定语境按设计未触发，属**柔性约束的实证而非形式化保证**。
